# Bring-your-own IdP federation on AWS: findings and reproduction

**Status:** live AWS proof completed September 25, 2026, in `us-west-2`. All 16 checks with a predetermined expected outcome passed. A seventeenth case observed that a future `nbf` was rejected. GCP, Azure, and two independently configured issuers sharing signing keys remain pending.

No AWS account ID, account-specific resource ARN, private signing key, token, or cloud credential is included in this report. Supply the destination account through the local `AWS_ACCOUNT_ID` environment variable.

## What was proved

A locally signed RS256 JWT was exchanged through `sts:AssumeRoleWithWebIdentity` for temporary AWS credentials. Those credentials invoked a private Lambda and received `{"message":"hello world","cloud":"aws",...}`. The external JWT is not passed directly to Lambda and STS does not mint that original JWT.

```text
Local signer → external JWT → AWS STS → temporary AWS credentials → signed Lambda Invoke
                                   ↑
               public issuer discovery → public JWKS
```

The test separated two decisions: whether a token can assume a role, and whether that role can invoke the function. A control role trusted the same valid token but had no invocation permission; its Lambda request was denied.

## Exact account configuration

The authoritative, deployable definition is [infra/aws-template.json](../infra/aws-template.json). It creates one CloudFormation stack named `jwt-federation-example`, containing these five resources:

| Resource | Required configuration and purpose |
|---|---|
| IAM OIDC provider | URL `https://redbmk.github.io/jwt-federation-example`; client ID/audience allowlist contains `byo-idp-poc`. The provider is registered in the target AWS account. |
| Invoker IAM role | Trusts only this OIDC provider for `sts:AssumeRoleWithWebIdentity`, with exact `aud` and `sub` conditions shown below. One inline policy grants `lambda:InvokeFunction` on the exact Lambda ARN generated by the stack. |
| Lambda execution role | Trusts `lambda.amazonaws.com` for `sts:AssumeRole`. No AWS service-access policies: the handler requires none. CloudWatch logging permission was deliberately omitted. |
| Hello-world Lambda | Python 3.13, inline `index.handler`, 128 MB memory, 3-second timeout; no Function URL or API Gateway. Returns a message, cloud name and Lambda request ID. |
| Denied control role | Same OIDC trust as the invoker role, but no permission policies. Required only for the negative authorization control, not normal integration. |

Invoker trust policy, with a symbolic account placeholder (CloudFormation fills the provider ARN automatically):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::${AWS_ACCOUNT_ID}:oidc-provider/redbmk.github.io/jwt-federation-example"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "redbmk.github.io/jwt-federation-example:aud": "byo-idp-poc",
        "redbmk.github.io/jwt-federation-example:sub": "client:client-a:agent:agent-a"
      }
    }
  }]
}
```

Invoker permissions policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "lambda:InvokeFunction",
    "Resource": "${FUNCTION_ARN}"
  }]
}
```

The placeholders above are explanatory, not literal runnable policy values. The template uses resource references to resolve them without hard-coded account details.

**Permissions boundary:** none was attached to the test roles, and one is not a protocol prerequisite. If an organization requires boundaries, the template must set the approved boundary on each applicable role. A boundary limits permissions; it does not grant invocation or replace the trust policy. Applicable service control policies, boundaries and explicit denies can still prevent access. These organizational controls were not exercised by this proof. [AWS boundary behavior](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html)

**Lambda resource policy:** none was added. This is same-account, signed API invocation authorized by the invoker role's identity policy. Cross-account invocation is a separate configuration and was not tested. [AWS Lambda resource policies](https://docs.aws.amazon.com/lambda/latest/dg/access-control-resource-based.html)

**Other mechanisms:** no session policy, session tags, `sts:TagSession`, external ID, Cognito, IAM Identity Center, or JWT authorizer is involved. The role's audience and subject checks are exact string matches. The test requests 900-second STS sessions.

### Setup permissions versus runtime permissions

The setup instructions used a personal administrative IAM identity with browser-based CLI login. The experiment did not derive or validate a minimal deployment policy. Administrator access is not required by the JWT caller, nor is it claimed to be the minimum setup permission.

Provisioning needs permission to operate CloudFormation change sets/stacks and to create, inspect, update, tag and delete the template's IAM provider, IAM roles/inline policy and Lambda. It also needs `iam:PassRole` for the execution role passed to Lambda, which can be scoped with `iam:PassedToService=lambda.amazonaws.com`. This template supplies no separate CloudFormation service role. `CAPABILITY_IAM` acknowledges IAM creation; it does not grant permissions. An existing provider with the same issuer must be handled explicitly rather than silently adopted or deleted.

For an IAM identity using `aws login`, the setup guide includes `SignInLocalDevelopmentAccess`. That permission enables local login, not resource provisioning. At test time the operator profile only calls `sts:GetCallerIdentity` and `cloudformation:DescribeStacks` to check the account and discover generated ARNs. STS web-identity exchanges are unsigned requests using the JWT, and Lambda invocation uses only the returned temporary credentials. [AWS CLI login](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html), [STS API](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRoleWithWebIdentity.html)

## Issuer requirements and integration implications

The public discovery path is `https://redbmk.github.io/jwt-federation-example/.well-known/openid-configuration`. Its `issuer` equals the JWT's `iss`; its `jwks_uri` points to `https://redbmk.github.io/jwt-federation-example/jwks.json`. The public JWKS contains an RSA public key with `kid`, `use=sig` and `alg=RS256`. The private key stays local.

The token endpoint can have a different URL from the issuer. For example, `api.example.com/v2/oauth/token` may mint a JWT with `iss=https://auth.example.com`. To use that issuer in this AWS flow, discovery must be publicly reachable at `https://auth.example.com/.well-known/openid-configuration`; its JWKS may reside on `public.auth.example.com`. A public reverse proxy for the discovery path could preserve the existing issuer. Merely hosting discovery under another domain does not supply an AWS discovery-URL override. This private-issuer arrangement is a design implication, not something tested here. [AWS OIDC setup](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_create_oidc.html)

Our initial Pages artifact excluded `.well-known`; the corrected workflow preserves it and verifies both live files. The browser's download behavior for the extensionless discovery document did not prevent AWS federation in the successful run.

## Full observed outcomes

Baseline claims were `iss` equal to the Pages issuer, `aud=byo-idp-poc`, `sub=client:client-a:agent:agent-a`, `client_id=client-a`, and `agent_id=agent-a`. The signer adds integer `iat` and `exp`; normal tokens expire five minutes after minting and use `iat` 30 seconds in the past. Each mutation starts from that baseline.

| Case / mutation | STS exchange | Lambda invocation | Recorded result |
|---|---|---|---|
| Valid baseline | Allowed | Hello-world returned | Pass |
| `iss` changed to an unregistered `/untrusted` issuer | Rejected: `InvalidIdentityToken` | Not attempted | Pass |
| `aud` changed to `other-audience` | Rejected: `InvalidIdentityToken` | Not attempted | Pass |
| `sub` changed to client-b; `client_id` also changed | Rejected: `AccessDenied` | Not attempted | Pass |
| `sub` changed to agent-b; `agent_id` also changed | Rejected: `AccessDenied` | Not attempted | Pass |
| Only custom `client_id` changed | Allowed | Hello-world returned | Pass: field not enforced |
| Only custom `agent_id` changed | Allowed | Hello-world returned | Pass: field not enforced |
| Custom `client_id` removed | Allowed | Hello-world returned | Pass: field not enforced |
| Custom `agent_id` removed | Allowed | Hello-world returned | Pass: field not enforced |
| `sub` removed | Rejected: `InvalidIdentityToken`, missing sub | Not attempted | Pass |
| `exp` one hour in past | Rejected: `ExpiredTokenException` | Not attempted | Pass |
| Trusted `kid`, signature made with a different private key | Rejected: `InvalidIdentityToken` | Not attempted | Pass |
| `nbf` one hour in future, `exp` two hours in future | Rejected: `InvalidIdentityToken`, token not yet valid | Not attempted | Observation |
| Add `azp=other-client` | Rejected: `InvalidIdentityToken` | Not attempted | Pass |
| Valid baseline repeated after negative cases | Allowed | Hello-world returned | Pass |
| Valid token exchanged for the denied control role | Allowed | `AccessDeniedException` | Pass |
| Unsigned Lambda request | Not applicable | `MissingAuthenticationTokenException` | Pass |

The full run timestamp, individual function request IDs and returned service explanations are preserved in [results/aws-results.json](../results/aws-results.json). A compact version is in [results/AWS-RESULTS.md](../results/AWS-RESULTS.md).

The decisive limitation: AWS's default OIDC mapping does not expose arbitrary top-level custom claims as IAM condition keys. This proof enforces client and agent identity through `sub`; it does not enforce equality between `sub` and the custom fields. For AWS's default mapping, the `aud` condition key uses `azp` when present, and `oaud` maps to the original `aud`. Adding `azp` is therefore not a harmless extra claim. Our rejection is observed; its generic service error does not identify the exact internal validation step. [AWS OIDC claim mapping](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_iam-condition-keys.html#condition-keys-wif)

## Scripts and reproduction

Requires Node.js 22+, Python 3 and AWS CLI v2. Browser-based `aws login` requires CLI 2.32.0+. No third-party runtime packages are needed. Run from the repository root:

```sh
# Set this only in your local shell. Never put its real value in the repo.
export AWS_ACCOUNT_ID="<your-account-id>"

aws login --profile jwt-federation-example --region us-west-2
npm test
python3 scripts/aws-deploy.py

# Explicit minting example; the live test runner also does this automatically.
node issuer.mjs mint https://redbmk.github.io/jwt-federation-example byo-idp-poc
python3 scripts/aws-test.py
```

- [issuer.mjs](../issuer.mjs): generates public JWKS/discovery on initialization and signs the 14 token variants. Original initialization was `node issuer.mjs init https://redbmk.github.io/jwt-federation-example`; do not rerun it on the initialized checkout. A fresh clone needs access to the original private key to use the currently published JWKS, or a deliberately provisioned new issuer/key setup.
- [scripts/aws-deploy.py](../scripts/aws-deploy.py): validates `AWS_ACCOUNT_ID`, checks the active account and both published documents, then deploys [infra/aws-template.json](../infra/aws-template.json). Optional `--profile` and `--region` override defaults.
- [scripts/aws-test.py](../scripts/aws-test.py): validates the account, reads stack outputs, mints fresh JWTs, performs unsigned STS exchanges, and invokes Lambda with isolated STS credentials. Profile/config/environment credential fallback is disabled for test calls. It writes `.local/aws-results.json` and exits nonzero on a failed expected check.

The live run used these same scripts with the account supplied through their former required `--account` option. The repository now uses `AWS_ACCOUNT_ID` exclusively; this input change does not alter the trust policy, signing, exchange or invocation logic. The first live run exposed a report-classification bug for `ExpiredTokenException`; it was corrected and the entire live suite reran successfully. No cloud claim result has been simulated or inferred from local unit tests.

`.local/` and `.env` files are ignored. JWTs and credentials must not be copied into committed results. Commit only the reviewed, sanitized report. Cleanup commands are in [AWS.md](../AWS.md); the deployed stack was retained for follow-up tests. Light usage does not establish free-tier eligibility, and no zero-cost guarantee is made.

## Remaining tests and limits

- Two configured issuers sharing one JWKS: not yet run. Current wrong-issuer rejection uses an unregistered issuer.
- GCP and Azure: not yet run. Do not present their expected behavior as measured AWS-equivalent results.
- Session-tag-based custom claim authorization, permissions boundaries, SCPs, cross-account invocation, JWKS rotation/revocation, replay prevention and token caching: not tested.
- Some `InvalidIdentityToken` responses are generic. Successful baselines bracket the mutations; the report establishes acceptance/rejection for these inputs, not every internal reason.
- The signed JWT is a bearer credential; matching an issuer proves trust in its signing authority, not independent verification of the agent that requested minting.
